整体架构设计 —— 对标「流光剪辑」

以扣子（Coze）工作流为编排入口、全部服务运行在云端的自动化视频工厂。本方案对照 流光剪辑（VectCut）官方文档 的全部功能域，给出可直接落地的分层架构、子系统设计、API 规划与分期路线。

  • 决策 1 · 编排扣子是唯一调度入口：Bot 对话、工作流、定时触发、看板全在扣子侧，自建服务只做「能力执行者」。
  • 决策 2 · 引擎自建草稿引擎 + FFmpeg 渲染管线，时间线模型自持；P2 提供「剪映草稿导出器」获得二次编辑能力。
  • 决策 3 · AI 能力不重复造轮子：文案/生图/生视频优先复用扣子节点；引擎侧只承接草稿必需的 TTS、ASR、素材处理等能力，多供应商适配。
  • 决策 4 · 异步渲染与 AI 任务统一走「任务总线 + Webhook 回调 + 看板对账」，绕开扣子工作流同步执行时长限制。

§1

对标分析：流光剪辑的功能全景

流光剪辑（VectCut）是一款云端 AI 批量剪辑工具：用户编排剪辑任务，由 AI 批量、自动化执行剪辑，产出投放到短视频与社交媒体，替代重复人工操作。它的四大卖点是：云端剪辑 API 与 Skill 工具包（字幕、插图、画中画、AI 配音、滤镜等）、丰富的 AI 生成能力（生图、生视频、配音、数字人）、高并发云端渲染（弹性扩容）、以及导出剪映草稿二次编辑，见 流光剪辑官方文档。

1.2 它的方法论：人机分工三层

其教程给出了值得沿用的设计理念：「人 × AI 对话」负责想清楚（确定风格、节奏、结构），「工作流」负责定下来（把怎么剪沉淀为可复用的标准流程），「API 精确执行」负责干精细活（裁剪、拼接、转场、字幕），见 Codex 上手教程·第一课。同时它明确「不做」：不做全 AI 自动化、不做数字人 IP、不做基础剪辑工具、不做 AI 大模型——这个边界感同样是个人系统该有的。

AI 视频生产的固定四阶段也直接沿用为其流水线的骨架：① 文案（主题、角度、脚本、口播内容）→ ② 语音合成（AI 配音/真人录音/数字人声音，决定节奏与听感）→ ③ 素材准备（图片、视频片段、字幕、贴纸、背景、转场、B-roll）→ ④ 视频合成（时间线组合语音、素材、字幕、音乐、特效，渲染成片）。

个人版的目标：在扣子里说一句话或填一行表格，就能跑完「文案 → 配音 → 素材 → 草稿 → 云渲染 → 成片回表」全链路；批量场景（口播、混剪、带货、信息流）日产几十到上千条；关键工程资产（草稿模型、模板库、渲染能力）沉淀在自己手里，不依赖单一第三方额度与定价。

§3

核心子系统设计

六个子系统对应 §1 的八个功能域。每个子系统给出职责、关键数据结构与实现要点，接口路由见 §6 映射表。

3.1 草稿引擎（对标 draft 体系）

系统的核心资产。一个「草稿」就是一份时间线工程 JSON，与剪映草稿同构但更简洁：轨道（track）承载片段（segment），片段引用素材（material），支持层级叠加实现画中画、关键帧驱动动画。草稿可被增量编辑——每个 add_* / modify_* / remove_* 都是对该 JSON 的一次事务更新，随时 GET /drafts/{id}/script 检查，确认无误再提交渲染（对应流光的 query_script 先检查后渲染的做法）。

  "draft_id": "dfd_20260917_0001",
  "name": "口播_绘本好物_01",
  "canvas": { "width": 1080, "height": 1920, "fps": 30 },
  "tracks": [
    { "type": "video", "name": "video_main", "level": 0,
      "segments": [
        { "segment_id": "seg_v1", "material_id": "mat_hook",
          "start": 0.0, "end": 3.2, "source_start": 0.0,
          "transform": { "x": 0, "y": 0, "scale": 1.0, "alpha": 1.0, "rotation": 0 },

                         { "t": 3.2, "prop": "scale", "v": 1.0 } ],
          "transition_in": { "type": "叠化", "duration": 0.5 } } ] },

关键设计

轨道层级 = 画中画

level 数字即图层顺序（0 底层），叠加图片/视频即可做画中画、贴片、水印、名片；「字在人后」用「人像抠像轨 + 文字轨（level 更低）」两轨组合实现，与流光抠像接口的产出方式一致。

关键设计

素材入场即校验

每次添加素材时异步探测真实时长/分辨率（对标 get_duration / get_resolution），时间线引用前先落库；渲染前再做一次全草稿引用完整性校验，避免「黑屏段」。

关键设计

模板化样式引用

文字/字幕的字体、描边、阴影、花字效果不在草稿里散落参数，而是引用样式模板 ID，全片换风格只改一处——这是批量生产「统一包装」的基础。

关键设计

可导出剪映草稿

时间线模型与剪映 draft_content.json 概念同构，P2 提供导出器把草稿翻译为剪映草稿文件，下载后在剪映里精修——复刻流光「云端生成 + 剪映二次编辑」的差异化能力。

3.2 工作流脚本解释器（对标 execute_workflow）

批量场景下，逐条调用 add_* 接口请求次数多、往返慢。提供一段 DSL 脚本在引擎内一次性执行：支持四种步骤（action / if / for / set_var）与 ${inputs.x} 变量替换，脚本可发布为 workflow_id 复用——接口形态与流光的 execute_workflow 保持一致，方便心智迁移与扣子节点封装。

POST /api/v1/workflows/execute
{
  "inputs": { "title": "哄睡神器", "audio_url": "https://oss/tts/01.mp3",
              "images": ["https://oss/img/1.jpg", "https://oss/img/2.jpg"] },
  "script": [
    { "type": "action", "id": "s1", "index": 0, "action_type": "add_audio",
      "params": { "audio_url": "${inputs.audio_url}", "start": 0, "track_name": "audio_main" } },
    { "type": "for", "id": "s2", "index": 1, "list": "${inputs.images}", "as": "img",
      "do": [ { "type": "action", "id": "s2a", "action_type": "add_image",
                "params": { "image_url": "${img}", "start": "${loop.index*3}",
                            "end": "${loop.index*3+3}", "track_name": "image_main" } } ] },
    { "type": "if",  "id": "s3", "index": 2, "cond": "${inputs.title}",
      "then": [ { "type": "action", "id": "s3a", "action_type": "add_text",
                  "params": { "text": "${inputs.title}", "start": 0, "end": 3,
                              "track_name": "title_main", "style_ref": "tpl_title_hv" } } ] }
  ]
}   →  { "success": true, "output": { "draft_id": "dfd_…" } }

实现为 Python 单遍解释器：动作注册表直接进程内调用草稿引擎函数（不走 HTTP），表达式求值只开放算术与索引访问，杜绝注入面。发布的工作流存 PostgreSQL，带版本号，可 list / get 检索。

3.3 AI 技能聚合层

先复用、再自建：文案生成、AI 生图、AI 生视频在扣子里有现成节点（LLM、图像、视频生成工具），直接在 L0 用扣子节点完成，产物 URL 传给引擎——不重复建设、还少一层费用。引擎侧只承接「草稿链路必需、且扣子节点不便承接」的能力：TTS 成片级配音、ASR 词级时间戳、抠像、变声、超分、平台解析等素材处理类任务。

统一任务模型：短任务同步返回（探测、提取音频），长任务一律异步——POST …/submit 返回 task_id，GET …/tasks/{id} 查询，完成时 Webhook 回调。每个能力配 1 个供应商适配器，可配置主备降级（如 TTS：豆包主用、MiniMax 备用），应对单家限流或涨价。

3.4 云渲染农场

渲染是全系统最重的计算，设计成队列驱动 + 无状态 Worker：

  1. 取任务渲染管线六步之首：按优先级从 Redis 队列取草稿快照，锁定防重复消费
  2. 素材预取并发下载全部素材到本地缓存盘；命中缓存直接复用（同一模板批量出片时收益巨大）
  3. 时间线编译草稿 JSON → FFmpeg filter_complex 图：片段裁剪/缩放/定位/透明度 → overlay 叠轨；关键帧 → sendcmd/表达式动画；转场 → xfade；滤镜 → LUT；贴纸/水印 → PNG overlay；音频 → adelay+amix；字幕 → 生成 ASS 由 libass 烧制
  4. 渲染FFmpeg 软编 H.264/H.265，分辨率与帧率取自画布配置；长视频按场景分段渲染再拼接，失败只重跑坏段
  5. 后处理封面抽取（首帧或指定帧）、成片上传 OSS、写回任务表（时长/大小/md5）
  6. 回调Webhook 通知扣子（带签名），更新看板状态
队列设计

三级优先级 + 闲时渲染

高：交互式单条（对话里等结果）｜中：批量生产｜低：闲时渲染（对标 generate_idle_video：深夜/低成本时段自动消化，价格敏感的批量任务全走这档）。失败任务指数退避重试 2 次，仍失败进死信队列 + 告警。

弹性伸缩

按队列深度扩缩 Worker

Worker 是无状态 Docker 镜像（FFmpeg 7 + 中文字体 + libass）。伸缩器每分钟检查队列深度：积压 > N 则向云厂商按量池/K8s HPA 申请新 Worker，空闲即释放——复刻流光「弹性扩容、秒级扩容」的核心体验，但规模为个人量级（1→10 台）。

效果覆盖

效果映射表是长期资产

剪映系效果名 → FFmpeg 滤镜实现的映射表（转场 40+、滤镜 60+、常用关键帧动画），随使用逐步补齐。这是自建渲染的护城河，也是 §9 中「覆盖边界」风险的应对手段。

渲染副产物

预览小样

渲染前可用「降分辨率 + 前 5 秒」快速出预览小样（占用 1/10 算力），口播/混剪批量场景先看小样再决定是否上正式渲染，省大量无效渲染费。

3.5 模板与预设中心

批量生产的效率来源。三层结构：

  • 预设（preset）：一段参数化的片段组合 JSON（如「片头贴片 3s」「结尾名片 5s」），add_preset 一发入草稿，可分组管理——对标流光预设体系。
  • 样式模板：字幕/标题的花字、字体、描边、动画打包成样式 ID，草稿按引用挂载，全片统一换装。
  • 场景模板（Agent 任务制）：口播模板 = 固定版式骨架（标题区/字幕区/贴片位）+ 参数（文案、音色、配图规则）；混剪模板 = 素材池 + 卡点规则 + 镜头时长分布。提交参数即启动一个引擎侧编排任务（对标 submit_agent_task + task_status），内部由 LLM 辅助分镜、由解释器执行编排。

3.6 素材库与存储

  • 对象存储三分区：/assets 常驻素材（挂标签、时长、分辨率、来源元数据）；/tmp 临时上传区（12 小时生命周期自动清理，对标流光临时文件 12h 失效）；/output 成片区（按项目/日期归档，冷数据转低频存储）。
  • 素材元数据表：类型、标签、时长、分辨率、来源（上传/解析/AI 生成）、关联草稿——支撑「按关键词挑素材」做混剪。
  • 上传通道：POST /api/v1/assets/upload 返回预签名直传 URL，扣子侧只传 URL 不传文件体，避免大文件过工作流。
§4

扣子集成方案（关键章节）

扣子负责「想」与「调」，引擎负责「干」。集成要解决两件事：工具怎么暴露给扣子，以及长耗时任务怎么在扣子工作流的同步执行模型里优雅落地。

4.1 三种接入方式

表 4-1 · 引擎能力暴露给扣子的三种方式
方式做法适用结论
扣子插件按功能域把 API 写成 OpenAPI Schema 导入扣子插件（草稿管理 / 素材编排 / 工作流 / 渲染任务 / AI 技能五组工具），工作流中拖节点即用所有常规调用；参数有下拉与校验，最稳主方案。维护一份 Schema 即同时服务工作流与 Bot 工具调用
HTTP 请求节点工作流内直接配 URL + Body 调引擎调试期、临时取数、插件未覆盖的新接口补充手段
MCP Server引擎暴露 MCP，供 Agent 模式/外部 Agent 使用想让其他 AI Agent（如 Claude Code）也能驱动同一套引擎P2 可选，接口层天然兼容

4.2 长任务三模式（渲染 3~15 分钟 vs 工作流分钟级时限）

核心矛盾：扣子工作流是同步执行模型，不适合原地等待渲染。三种模式按场景组合：

模式 A

拆流轮询（调试与低频）

「提交工作流」返回 task_id 即结束；另建「查询工作流」，用循环节点隔 N 秒调 GET /render/tasks/{id} 直到终态。适合：单条试跑、验证链路。注意：循环次数与执行总时长受扣子节点限制，等待长渲染时不可靠。

模式 B

Webhook 回调（推荐主力）

引擎渲染完成后回调扣子触发入口（Webhook/触发器），携带 task_id 与成片 URL，启动「后续工作流」：更新看板 →（可选）发布流 → 通知你。提交即忘，无轮询开销。适合：单条与批量主力链路。

模式 C

定时批量对账（批量兜底）

扣子定时触发器每 5~10 分钟跑「对账工作流」：调引擎 GET /render/tasks?status=finished&since=… 拉取终态任务，批量回写看板。适合：批量场景兜底 + 回调丢失补偿。B+C 双保险，状态最终一致。

4.3 任务状态机（引擎侧统一，扣子侧只读）

QUEUED→ RUNNING→ SUCCESS │ FAILED→RETRY×2→QUEUED │ CANCELED

每个任务携带 kind（render/tts/asr/matting…）、cost（记账）、draft_id、callback_url。扣子看板上的「状态列」即此状态机的投影。

4.4 生产看板（对标飞书表格「一条记录=一条视频」）

沿用流光验证过的管理范式，放扣子生态内：用扣子多维表格（或飞书多维表格，可经飞书 CLI 同步），一行 = 一条视频任务，工作流自动回写：

输入列（人填/LLM 填）：主题、文案、目标平台、比例、音色、模板 ID、素材链接
过程列（引擎回写）：audio_url、draft_id、render_task_id、预览小样 URL
结果列（自动）：成片 URL、时长、大小、状态、失败原因、成本（元）
经营列（人填）：发布平台、发布链接、数据反馈 → 反哺爆款知识库

「在表格里搭建视频生产系统」是流光主推的团队协作范式，见 其飞书表格教程；本方案将其移入扣子生态，由定时触发器与回调驱动，无需人工刷表。

§5

端到端数据流：以「批量口播」为例

一条扣子工作流串起四阶段生产流程，全程无需人工干预，人只看最后成片。

  1. 入口 · 建单多维表格新增 N 行主题（或对话「给我出 20 条绘本好物口播」）→ 定时触发器/按钮启动批处理工作流
  2. 阶段① 文案扣子 LLM 节点按主题 × 爆款结构（知识库）生成 N 条口播文案，回写表格 扣子内
  3. 阶段② 语音循环每行：调 /ai/tts/submit（豆包音色）→ 回调拿 audio_url → /media/probe 取时长 引擎
  4. 阶段③ 素材封面/首帧：扣子生图节点出图；配图：按文案关键词从素材库选或生图；ASR 提交 audio_url 得词级时间戳 扣子+引擎
  5. 阶段④ 组装调 /workflows/execute（口播模板 workflow_id + inputs：文案/音频/图组/字幕模板）→ 返回 draft_id；可选先出预览小样 引擎
  6. 渲染提交POST /render/tasks（闲时档）→ render_task_id 回写表格，状态=渲染中 引擎
  7. 完成回写Webhook 回调（模式 B）→ 工作流更新状态=已完成 + 成片 URL；每 10 分钟对账工作流兜底（模式 C）引擎→扣子
  8. 人工收口看板筛「已完成」，抽查 10%~20% 精修（可下载草稿在剪映二改，P2 能力），其余直接投放 人

混剪、信息流广告复用同一骨架，仅替换阶段③④的模板与素材规则——这正是「四阶段固定流程 + 模板化」的意义：换赛道不换系统。

§9

成本与风险

9.1 成本结构（量级估算，以实际账单为准）

  • 渲染：1080p 竖屏 60s 成片，CPU 软编约消耗 2~4 核·分钟量级；按量 Worker 单条成本约在几分到一角钱人民币量级，批量走闲时档更低。TTS 与扣子节点调用按各家计费，量产后建议每月复盘一次供应商比价——这正是自建聚合层的价值。
  • 固定开销：控制面一台轻量服务器 + OSS/Redis/RDS，月成本可控制在百元级。
  • 记账纪律：任务级成本台账（§2 横切）从 P1 起强制执行，看板直接展示每条视频成本，避免「量上去了、账爆了」。
